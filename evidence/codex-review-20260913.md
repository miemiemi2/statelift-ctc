## 已核实的问题

1. **接力状态误报。** `cli/operator.mjs:911` 计算所有旧轮次的 `anyPendingPastT`，`:949` 用它判断可以开启下一轮。E1 过 T1 仍 Pending、E2 已开启但 T2 未到时，status 会说可以开 E3；`StateLiftGoalEscrow.sol:417` 则只看最后一轮并以 PreviousRoundStillLive 拒绝。合约的约束仍在，错误在操作入口。本项由主审与 worker 分别核对源码；未新增链上复现测试。
2. **单目标状态中的金额口径不清。** `cli/operator.mjs:930` 的 recoveredCredits 读取运营者全局 credits。其他目标的退款会出现在当前目标下，且实际提款后余额归零也不代表本目标未曾退款。应区分本目标累计返还和账户当前可提取余额；链上资金账没有因此被混用。
3. **手动验收链路不完整。** README 幕 C 展示“旧付款已发生，替补被拒”；未付款分支停在 Released / 可接力，没有继续给出第二轮付款、结算和资金收尾。stage2-acceptance.md 的相关记录也停在可接力。合约测试、CLI 自动测试和 demo 脚本已有新人完成付款路径，因此这是手动出口与证据问题，不是该能力未实现。
4. **旧入口仍与新承诺冲突。** `npm start` 仍启动 web/server.mjs；web/app.js:12 写“已付款，就不能把预算退掉”，:17 写“先证明未付款，再释放预算”。这是旧方案的语义，不能直接作为当前保障版展示。CONCEPT.md、项目总状态入口与新的 IMPLEMENTATION.md 也未同步；总入口仍称工程尚未启动。
5. **重复付款测试的断言不稳定。** `tests/source/goal-router.test.cjs:178` 只对 `s.fill(...)` 的交易提交 Promise 做 rejects，未等待链上回执。本次全量跑到这里报 Missing expected rejection；单项复跑则在提交前被拒。额外诊断在内存中给交易设置明确 gasLimit，跳过估算：发送交易返回成功，但等待回执得到 status=0 / CALL_EXCEPTION，收款人余额仍为 5000000000（仅一笔）。因此“提交返回”不能作为“链上付款成功”的判断。需要让该测试检查最终回执及余额；原始全量失败与 ethers 估算缓存的具体关联尚未单独验证。诊断未修改仓库测试或产品代码。
